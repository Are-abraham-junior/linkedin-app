# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Bleadin** (aka "Bime Link") — a LinkedIn prospection/automation SaaS. Node/Express/Prisma API + React/Vite SPA, backed by Postgres (Neon serverless) and the Unipile API for all LinkedIn actions (invitations, messages, profile visits, follows, webhooks).

## Commands

```bash
npm run dev              # runs API (tsx watch) + client (vite) concurrently
npm run dev:server       # API only, server/src/index.ts via tsx watch
npm run dev:client       # client only (npm --prefix client run dev)

npm run build            # client install+build, then prisma generate — used for local/Render-style deploys
npm run build:server     # tsc compile of server/ + lib/ + prisma/ per tsconfig.json -> dist/
npm run build:client     # npm --prefix client run build
npm run build:production # tsc --outDir dist + prisma generate (used for cPanel packaging)

npm run prisma:generate  # prisma generate
npm run prisma:migrate   # prisma db push (no migration files — schema is pushed directly)
npm run prisma:seed      # tsx prisma/seed.ts

npm run verify           # tsx scripts/verify-prisma.ts
```

There is no lint or test script configured — verify server changes with `npm run build:server` (tsc) and client changes with `npm --prefix client run build` (tsc + vite build). There is no test suite.

### Deployment (cPanel LWS / Passenger, single-command CLI)

`scripts/cpanel-remote.js` drives everything: `build`, `package` (assembles `deploy/`), `push` (SCP/SSH), `chmod` (755 on `dist/`), `restart` (Passenger `touch tmp/restart.txt`), `logs` (tail stderr.log), `diag` (direct `node app.js` run inside `nodevenv` to unmask Passenger 500s), `db-push`, `health` (curl `/api/health`), and `deploy-all` (the full pipeline). Corresponding `npm run deploy:*` / `remote:*` scripts wrap these. Config comes from `.env.deploy` (see `.env.deploy.example`), falling back to `.env`.

## Architecture

### Monorepo layout
- `server/src/` — Express 5 API in TypeScript, compiled to `dist/` via top-level `tsconfig.json` (`rootDir: ./`, includes `prisma/`, `lib/`, `server/`). Entry point `server/src/index.ts`.
- `client/` — separate React 18 + Vite + TypeScript app with its own `package.json`/`tsconfig.json`, built independently and served as static files by the API in production (`client/dist`).
- `lib/prisma.ts` — the single Prisma client instance, imported by server code as `../../../lib/prisma.js` (note the compiled `.js` extension convention — this is an ESM project, `"type": "module"`, `module: NodeNext`).
- `prisma/schema.prisma` — one flat schema, no migrations folder; schema changes are pushed directly with `prisma db push`.
- `deploy/` — pre-assembled production bundle (built `dist/`, `client/dist`, `prisma/`) that `cpanel-remote.js package`/`push` produce and ship to the cPanel host. `app.js` at repo root is the Passenger entry point.
- `.agents/skills/` — a set of domain-specific "skill" docs (prisma, unipile-linkedin, postgresql, api-architect, backend, express, node_expert, react_expert, frontend-dev, fullstack, cpanel-lws-expert, debugger, skill-creator) referenced by the multi-agent orchestration doc `AGENTS.md`. That doc describes a Gemini-style sub-agent orchestration workflow with named playbooks for campaign queues, Unipile sync, prospect imports, and dashboard/design work — useful background on intended domain boundaries even though it targets a different agent runtime.

### Server: multi-tenant data model
Prisma schema (`prisma/schema.prisma`) centers on:
- `Organization` → `User` (roles: `SUPER_ADMIN`/`USER` for platform role, `OWNER`/`ADMIN`/`MEMBER` for org role). Auth is JWT (`server/src/middlewares/auth.middleware.ts`), 7-day tokens, `requireAuth`/`requireSuperAdmin`. Super admins can impersonate an org via the `x-impersonate-org` header, which swaps `req.user` to the org owner's identity while retaining `SUPER_ADMIN` privileges (`isImpersonating`/`originalSuperAdminId`).
- `LinkedInAccount` (linked via Unipile, one per user) tracks daily send counters, connection status, and account type (STANDARD/PREMIUM/SALES_NAVIGATOR/RECRUITER).
- `ProspectList` → `Prospect` (CRM entities, dedup on `linkedinUrl`), with `providerProfileId` resolved lazily from Unipile ("ACo..." LinkedIn internal IDs).
- `Campaign` → `CampaignStep` (ordered sequence: INVITATION/MESSAGE/VISIT_PROFILE/FOLLOW/DELAY, each with `delayDays` and templated `messageText`) → `ProspectCampaignState` (per-prospect progress through a campaign) → `ActionQueue` (the actual scheduled/executed actions).
- Automatic e-mail reports: per-user prefs are real `User` columns (`reportEmailFrequency`, `reportEmails[]`, `reportHour`, `reportDay`, `reportLastSentAt`, interpreted in `User.timezone`), driven by `server/src/workers/report.worker.ts` (15-min tick, at most one send per local day). The e-mail carries the full report as **PDF + Excel attachments**, generated server-side by `server/src/services/reportExport.service.ts` (jsPDF + xlsx in Node — a deliberate mirror of `client/src/utils/reportExport.ts`; keep the two in sync when changing the export layout). Export history still lives in the `IntegrationConfig` JSON blob with `provider = BLEADIN_REPORTS` (`reportSettings.service.ts`); a one-shot `migrateLegacyReportPrefs()` at scheduler start moves any leftover `config.users` prefs to `User`.
- **Enrichment tokens** (`EnrichmentLedger`, `server/src/services/enrichment.service.ts`, `/api/enrichment`): e-mail/phone are revealed only on demand — 1 token per e-mail found, 5 per phone found, reserved before the Unipile lookup (advisory lock per org) and refunded when not found. Monthly allowance per plan (`enrichmentTokens` in `config/plans.ts`, shared by the organization, no carry-over) + admin grants (`POST /api/admin/organizations/:id/enrichment-grant`). Each lookup counts as a profile visit in `quota.service.ts` and is refused when the day's visit target is reached. **The free paths (campaign visits, "Synchroniser") must never write `Prospect.email`/`phone`** — only title/company/avatar.
- `Conversation`/`Message` mirror Unipile inbox chats; `ImportHistory` tracks CSV/XLSX imports; `ApiKey`, `IntegrationConfig`, `Invoice` support org-level admin/billing features.

Routes live in `server/src/routes/*.routes.ts`, each paired with a same-named controller in `server/src/controllers/`, mounted in `server/src/index.ts` under `/api/<resource>` (auth, admin, user, lists, prospects, linkedin, campaigns, inbox, team, queue, settings), plus a standalone webhook endpoint `POST /api/webhooks/unipile`. In production the same Express app also serves `client/dist` and falls back to `index.html` for any non-`/api` GET (SPA routing).

### Campaign engine (`server/src/workers/campaign.worker.ts`)
This is the core automation loop, started via `startCampaignScheduler()` from `index.ts`:
- `processActionQueue()` runs every 60s: pulls up to 10 due `ActionQueue` rows, and for each checks (in order) account connection status, user's working hours/days (per-user `timezone`, computed with `Intl.DateTimeFormat`), campaign still ACTIVE, and quota. Quotas are **per plan, weekly + monthly** (`server/src/config/plans.ts`, mirrored in `client/src/marketing/content/plans.ts` — keep both in sync) for INVITATION / MESSAGE / VISIT_PROFILE / FOLLOW, enforced by `server/src/services/quota.service.ts`: usage is counted live from `ActionQueue` rows (SUCCESS/EXECUTED) since local day / Monday / 1st of month in the user's timezone; the **daily target is derived, never stored** — `remainingWeek / workingDaysLeft × U(0.75,1.15)` with a deterministic per-(account, action, date) jitter, capped by Unipile's daily safety caps (`DAILY_SAFETY_CAPS`) and the monthly remainder, halved/ramped during the 14-day warm-up after `LinkedInAccount.createdAt`. `User.maxWeekly*` (null = plan) can only lower the plan's weekly quota. Blocked actions are deferred to tomorrow 9h / next Monday 9h / 1st of next month 9h (local). The cached `dailyInvitesSent`/`dailyMsgSent` counters on `LinkedInAccount` are display-only and resynced opportunistically. Then dispatches to `UnipileService` (`sendInvitation`/`sendMessage`/`visitProfile`/`followProfile`), personalizing `{{firstName}}`/`{{lastName}}`/`{{company}}`/`{{headline}}` template variables, resolving `providerProfileId` on demand via `resolveProviderId()`, and on success enqueues the campaign's next step (or marks the prospect COMPLETED) and enriches the prospect record (email/phone/avatar/headline/company) from any profile data returned.
- Unipile errors are triaged by `categorizeUnipileError()` into DISCONNECT_ACCOUNT (checkpoint/401 → marks the `LinkedInAccount` DISCONNECTED, pauses the user's active campaigns, and requeues the action 2h later), DEFER_ACTION (429/rate-limit → requeues 15 min later), or CONTINUE (marks that single action FAILED without affecting the account).
- `checkAcceptedInvitations()` runs every 5 min: polls Unipile profiles for prospects in `WAITING_CONDITION` (invitation sent, awaiting acceptance) and advances them to the next campaign step once `network_distance`/`connection_status` shows a 1st-degree connection.
- When touching this file, preserve the ordering of checks (connection → working hours → campaign active → quota), never reintroduce a constant daily quota (LinkedIn flags regular patterns), and the "account-level failure breaks the batch loop, prospect-level failure just marks FAILED and continues" distinction — it's what prevents burning through the whole queue against a disconnected/rate-limited account.

### Client (`client/src/`)
- React Router v7 SPA (`App.tsx`), split into a public shell (`/connexion` — `/login` is only an internal alias because the LWS edge resets connections on that exact path — `/join`, `/setup`) and an authenticated `AppLayout` shell wrapping `Sidebar` + `Header` + route `Outlet` for `/dashboard`, `/campaigns`, `/prospects`, `/inbox`, `/team`, `/settings`, and super-admin-only `/admin`, `/admin/users`.
- Auth/session state lives in `client/src/context/AuthContext.tsx`; API calls go through `client/src/services/api.ts`.
- Components are organized by feature under `client/src/components/` (admin, auth, campaigns, dashboard, inbox, layout, modals, profile, prospects, settings, common).
- UI language is **« éditorial sobre »** (2026-09 refonte): white/ivory surfaces, hairline borders, no shadows except popovers/modals/toasts (`shadow-pop`), radii 8/12/16px (`rounded-lg` controls, `rounded-xl` inner blocks, `rounded-2xl` cards/modals), 14px body, headings in General Sans via the global `.display` class, Electric Violet `#592eff` **only** for the primary CTA, the active nav item and focus rings — never as a background wash, gradient, tinted icon chip or status pill. Colors are semantic tokens declared as RGB channels in `client/src/index.css` `:root` and mapped in `tailwind.config.js` (`ink`, `ink-2`, `muted`, `muted-2`, `line`, `line-2`, `surface`, `surface-2`, `canvas`, `accent{,-hover,-active,-soft}`, `ok`/`warn`/`danger` + `-soft`), so `bg-accent/10` style opacities work; never hard-code `#592eff`/`#21164c` in components. Shared primitives live in `client/src/components/ui/` (`Button`, `IconButton`, `Card`, `Stat`/`StatRow`, `Badge`/`StatusDot`, `Tabs`, `Field`/`Input`/`Select`/`Textarea`/`Checkbox`/`Switch`, `Modal` (portal, focus trap, Esc, single backdrop, `side="right"` drawer, `zIndex` for nesting), `Toast` (`useToast`, replaces `alert()`), `ConfirmProvider` (`useConfirm`, replaces `window.confirm`), `Skeleton*`, `EmptyState`, `PageHeader`, `Table` kit, `Avatar` (+ `avatarFallback.ts` data-URI initials — never `ui-avatars.com`), `Tooltip`, `Callout`); `common/ConfirmModal` keeps its historical props API on top of `Modal`. Icons: lucide, `strokeWidth={1.75}`, bare (no colored chip); `Sparkles` is reserved for the Bleadin IA page. `tailwind.config.js` overrides `fontSize` (xs 12 → 3xl 30) and `borderRadius.card/shot` exist only for `src/marketing/`. Editing `tailwind.config.js` requires restarting the Vite dev server (config is not hot-reloaded). Styling stays inline Tailwind (no component-class CSS layer); `DESIGN (2).md` documents the older Adora palette and is historical.

### Bleadin IA (`server/src/services/ai/`, `/api/ai`, `/api/admin/ai-*`, client `components/assistant/`)
Chat agent (route `/bleadin-ia`, plans PRO/BUSINESS + SUPER_ADMIN via `middlewares/aiAccess.middleware.ts`) that searches LinkedIn, builds lists, drafts campaigns and prepares launches. No LLM SDK: `ollama.client.ts` talks to Ollama's native `/api/chat` (streaming NDJSON + tools) or an OpenAI-compatible `/v1/chat/completions` using plain `fetch`. Providers are **rows in `AiProvider`** (one `isActive`), managed by the super admin at `/admin/settings` → « Providers IA » — the tunnel URL is ephemeral, so never hardcode it. Key design points:
- `tools.ts` reuses the existing controllers through `invokeController()` (fake req/res) so validation, scope rules and quotas stay in one place. Drafts are created with `listIds: []` (a draft saved with lists creates PENDING `ProspectCampaignState` rows that later block enrolment); the real launch re-`POST`s `createCampaign` with `{id, listIds, startImmediately: true}` (`launchDraftCampaign`) — `toggle-status` only flips the status and never enrols.
- Sensitive actions require a user click: `request_launch_confirmation` and `delete_prospect_list` emit a single-use 10-min token stored in `AiConversation.workspace.pendingConfirmation` (`kind: "launch" | "delete_list"`); the client posts `{confirmToken}` to `/conversations/:id/messages` and `executeConfirmedAction()` dispatches on `kind`.
- Existing campaigns: `get_campaign_details` / `update_campaign_steps` (partial `{stepOrder, messageText?, delayDays?}` patches). `applyCampaignStepPatches()` re-`POST`s `createCampaign` for the agent's own draft and calls `updateCampaign` (PUT, which also resyncs queued `ActionQueue` rows) for any other campaign; the `campaign_steps` card allows inline edit of messages **and delays** via `POST /conversations/:id/update-campaign`. Tools may declare `aliases` (names small models tend to invent, e.g. `update_prospect_list` → `rename_prospect_list`).
- `agent.service.ts` runs a bounded tool loop (≤6 iterations, 24-message history, per-turn state summary + BM25 knowledge retrieval in the system prompt). Small models (llama3.1:8b) sometimes emit tool calls as raw text (even inside prose or code fences) or pass arrays as JSON strings — `extractTextualToolCalls()` recovers them (unknown names included, so the loop answers « outil inconnu » instead of leaking JSON), `createDeltaGate()` withholds JSON-looking deltas from the UI, and array schemas go through `parseArrayIfString`. Tool result `note`s must never mention tool names (the model parrots them).
- Knowledge base: `AiKnowledgeDoc` rows seeded from `services/ai/knowledge/*.ts` (`seedKnowledgeIfEmpty()` at boot, `reseed` from the admin tab), `isCore` docs always injected, others retrieved by `knowledge.service.ts` (in-memory BM25 over `#`/`##`/`###` sections, invalidated on admin edits). `seedKnowledgeIfEmpty()` also inserts any seed doc whose slug is missing, so shipping a new `knowledge/*.ts` file is enough; editing an existing one needs the admin « Réinitialiser » (reseed). Plan/quota figures in `bleadinApp.ts` are generated from `config/plans.ts`.
- Context budget: `AiProvider.numCtx` (default 16384, admin-editable) is sent as Ollama `num_ctx`, and `thinking` (default false) as `think` — qwen3.5 otherwise spends its budget in a hidden `thinking` field and returns an empty message when the 8k window is full (symptom: no tool call, only the fallback « résumé » reply, which looks like amnesia). `fitHistoryToContext()` drops the oldest history messages (~3 chars/token estimate) so system prompt + history fit; near-saturation and empty responses are logged with `prompt_eval_count`. The system prompt alone is ~15k chars, so never go back to 8k.
- Output guard (`sanitize.ts`): the final assistant text is regex-cleaned (code fences, tool JSON, tool names → user phrases) and, if `hasTechnicalJargon()` flagged the original (tool/param names, snake_case, JSON), rewritten once by the model with `REWRITE_INSTRUCTION` (no tools). Whenever the persisted text differs from what was streamed, a `replace` SSE event swaps the current bubble (also emitted as `""` when a textual tool call is recovered from already-streamed prose). The prompt carries few-shot good/bad examples and the core doc lists real UI paths (« Chemins dans l'application ») so the agent can guide non-technical users by menu clicks instead of tool names.
- Benchmark: `npm run ai:bench` (`scripts/ai-bench.ts`, `--only=id,id`, `--out=file.json`, `BENCH_EMAIL/BENCH_PASSWORD/BENCH_API`) runs ~13 canned prompts through `stream:false`, creates/deletes its own fixtures, and checks no-jargon / expected tool / expected card — run it after prompt or tool changes and when comparing models (llama3.1:8b baseline 11-12/13, its remaining miss is a premature `draft_campaign` on « guide-moi »).
- SSE handler in `ai.controller.ts` catches everything itself (Express 5's global error handler would try `res.json()` on an open stream); `stream: false` returns full JSON as a fallback if a proxy buffers.
- Campaign sequence templates now live server-side in `config/campaignTemplates.ts` (`GET /api/campaigns/templates`, declared before `/:id`); the client wizard fetches them.

### Unipile integration
`server/src/services/unipile.service.ts` wraps the Unipile LinkedIn API ([docs](https://developer.unipile.com), [reference](https://developer.unipile.com/reference)) — account connection, invitations, messages, profile lookups/visits, follows. `server/src/controllers/webhook.controller.ts` handles inbound Unipile webhooks. LinkedIn's own internal profile identifier ("ACo..." `provider_id`) is distinct from `linkedinUrl`/slug and must be resolved via a profile lookup before most Unipile calls — see `resolveProviderId()` in the campaign worker for the caching pattern (store once resolved on `Prospect.providerProfileId`). The "Engagements d'un post" mode of the LinkedIn search modal (`POST /api/linkedin/post-engagers` → `UnipileService.getPost` + `getPostEngagers`) lists people who commented/reacted on a post; their `author.id` is already the provider_id, so those prospects are imported with `providerProfileId` pre-filled (`ImportHistory.source = LINKEDIN_POST`).

### Environment / config quirks
- `lib/prisma.ts` uses the standard `@prisma/adapter-pg` + `pg.Pool` driver adapter against the **PostgreSQL instance hosted on the LWS cPanel account itself** (`127.0.0.1:5432`). Connection mode (TCP vs Unix socket) and SSL are driven entirely by the contents of `DATABASE_URL`, so switching them is a config-only change (edit the remote `.env`, `touch tmp/restart.txt`) with no code redeploy. It resolves `DATABASE_URL` defensively (BOM, quoting, multiple `.env` locations) because of inconsistent env loading under Phusion Passenger.

- **CRITICAL — Prisma thread limiting on CloudLinux.** `lib/prisma.ts` and `env.js` both set `TOKIO_WORKER_THREADS=2` and `UV_THREADPOOL_SIZE=2` before Prisma is instantiated. Do not remove these. Prisma's Rust query engine sizes its Tokio thread pool from the visible CPU count (30 on this server), while CloudLinux caps the whole account at ~33 threads. Without the cap, thread creation fails with `EAGAIN`, the `futures-timer` thread dies, and the engine panics with `timer has gone away` — after which **every database query hangs forever with no actionable application-level error**. Symptoms are deceptive: `psql` and the raw `pg` driver keep working fine, only Prisma hangs. The setting must be applied in `lib/prisma.ts` (not only `env.js`) so that seed and maintenance scripts get it too.

- **CRITICAL — LWS blocks all outbound non-standard ports.** The server can only make outbound connections on ports 80/443; everything else (verified: 587, 993, 8080, 8443, 19478, 20000) is refused (`ECONNREFUSED`) instantly. Unipile's dedicated DSN uses a custom port (e.g. `:19478`), which made every Unipile call fail with a generic `fetch failed`. `server/src/services/unipile.service.ts` works around this using Unipile's own documented fix (https://developer.unipile.com/docs/api-usage): every request goes through the single `unipileFetch()` wrapper, which strips the port from the host and appends it as a `?port=XXXXX` query parameter instead, keeping the connection on standard 443. **Never call `fetch()` directly in this file — always use `unipileFetch()`** — and never revert `UNIPILE_DSN` handling to put the port back in the host while this app runs on LWS shared hosting.

- **CRITICAL — the API docroot sits *inside* the SPA's docroot, so `.htaccess` is inherited.** The Node app lives in `~/public_html/api-bleadin` (docroot of `api.bleadin.com`), which is a subdirectory of `~/public_html` (docroot of `bleadin.com`). Apache applies the `.htaccess` of **every parent directory** on the path to the requested file, so the front-end's SPA fallback (`RewriteCond %{REQUEST_FILENAME} !-f` / `!-d` → `RewriteRule . /index.html [L]`) also applies to the API vhost: any URL not matching a real file or directory in the API docroot — i.e. every Express route, including `/api/health` — was rewritten to an `/index.html` that does not exist there, yielding a **500 from Apache while the Node process was running perfectly** (`passenger.log` shows a normal `🚀 Bleadin API Server running on port 5000`). The tell-tale signature is that the HTTP status depends on whether the path exists on disk, not on the route: `/` and `/public/` (real directories) reached Express, `/package.json` (real file) returned 200, and every non-existent path returned 500. Three layers now prevent it, keep all three: (1) `client/public/.htaccess` guards the rewrite with `RewriteCond %{HTTP_HOST} ^api\.` + a `^api-bleadin` passthrough — this file is redeployed by `cpanel-remote.js package`, so the guards must survive any edit to it; (2) `scripts/api-htaccess-guard.conf` is appended once (idempotently, marker `BLEADIN-API-GUARD`) to the API's own `.htaccess` by `cpanel-remote.js push`, and a bare `RewriteEngine On` there discards the parent's rules entirely — mod_rewrite does not merge per-directory configs; (3) `cmdHealth()` probes a deliberately non-existent API route and fails the deploy (non-zero exit) if it returns 500 or SPA HTML instead of Express's 404. Both of its requests carry a cache-buster: LWS runs a Varnish edge in front of the site (`Edge-Cache-Engine: varnish`, `Age:` headers), and a cached 200 on `/api/health` will otherwise hide a dead app — during this outage the only non-500 response left was a 4-minute-old cached one. Note that the API's `.htaccess` also carries CloudLinux's `DO NOT REMOVE` Passenger block — never overwrite that file, only append to it.

- **Historical trap — database name with a space.** The original cPanel database was created as `c2862963c_ bleadin_db` (note the space). cPanel writes `pg_hba.conf` entries per database, so every connection attempt using the "logical" name failed with the misleading `no pg_hba.conf entry for host ... SSL off` — which was misdiagnosed (including by LWS support) as "external access disabled / no SSL support", and is what originally pushed this project onto Neon. The active database is now `c2862963c_bleadindb`. A cPanel PostgreSQL database only becomes reachable once a user is attached to it via `uapi Postgresql grant_all_privileges user=... database=...`; without that grant there is no `pg_hba.conf` entry and connections are refused regardless of credentials.
- `.env` (git-ignored) holds `DATABASE_URL`, `PORT`, `NODE_ENV`, `JWT_SECRET`, `UNIPILE_API_KEY`, `UNIPILE_DSN`, `UNIPILE_ACCOUNT_ID`. `.env.deploy` (see `.env.deploy.example`) holds SSH/cPanel deployment target config, separate from the app's own `.env`.
- In production, `SELF_PING_URL` (if set) triggers a self-ping every 4 minutes to keep the Passenger process from idling out.
